## 2026-09-21 — 프로젝트 시작

Deluge 저장소에서 작업하던 세션에서 "무관한 새 개발을 시작하고 싶다"는 요청으로 출발했다.
Deluge의 지침 문서가 매 턴 자동으로 얹히고 기억도 그쪽 이름공간에 쌓이기 때문에,
**새 폴더를 만들어 세션 자체를 옮겼다** (`D:\dev\BingoShare`, `git init`).

> 이 환경에는 새 세션을 띄우는 도구가 없어서 새 세션을 만들어 주지는 못했다.
> PC 앞에서 작업할 때는 이 폴더에서 세션을 새로 여는 편이 가장 깔끔하다.

### 기획 (`46e02b6`)

사용자가 고른 것: **각자 진행 + 현황판**, **칸 섞기는 만들 때 선택**, **무료 정적 호스팅**.

여기서 모순이 하나 나왔다. **현황판은 데이터를 모아야 하니 서버가 필요한데 정적 호스팅은
서버가 없다.** 호스팅은 정적으로 두고 데이터만 무료 BaaS에 맡기는 방향으로 풀되,
처음부터 다 만들지 않고 단계를 잘랐다 — **M1은 서버 0, M2에서 현황판.**

이때 정한 설계 원칙 하나가 이후 내내 기준이 됐다:
**진행 상황을 읽고 쓰는 통로를 어댑터 하나로 좁혀 둔다.** (`src/lib/storage.ts`)

## 2026-09-21 — M0 뼈대 (`43c3284`, `5fba2b1`)

Vite 8 + React 19 + TypeScript + Tailwind 4. 모바일 우선.

`vite.config.ts`의 `base`를 `'./'`로 뒀다. 루트든 하위 경로든 어디에 올려도 동작해서
호스팅을 갈아타도 코드를 고칠 일이 없다. 공유 링크가 해시를 쓰므로 히스토리 라우팅이
필요 없어 가능한 선택이다.

배포는 사용자가 "저장소도 만들어 달라"고 승인해 직접 처리했다.

- 이 PC에 `gh` CLI가 없어서 GitHub API를 직접 호출했다. 인증은 git 자격 증명 관리자에
  저장돼 있던 **`imjae` 계정 토큰**(`repo`, `workflow` 범위)을 썼고, 토큰 값은 출력하지 않았다.
- 공개/비공개는 결과가 갈리는 선택이라 사용자에게 물었고 **공개**로 정했다.
  (비공개였다면 GitHub Pages가 유료라 Cloudflare Pages로 갔어야 한다.)
- Pages의 빌드 소스를 `workflow`로 설정 → 첫 배포 성공.

## 2026-09-21 — M1 정적 공유 (`d00c0aa`)

만들기 → 링크 공유 → 참가 → 진행까지. 서버 없음.

판을 짧은 배열로 포장해 deflate로 압축하고 주소용 문자로 바꿔 `#b=…`에 담는다.
**해시를 쓰는 이유가 두 가지다** — 정적 호스팅에서 서버 설정 없이 동작하고,
해시는 서버로 전송되지 않아 판 내용이 접속 기록에 남지 않는다.

판 id를 **내용에서 뽑아낸다**(FNV-1a). 서버 없이도 "같은 판"을 판별할 수 있어서
진행 상황을 판별로 저장할 수 있다. 섞기 시드는 **판 id + 참가자 이름**에서 뽑아
새로고침해도 자리가 그대로다. 저장한 체크가 엉뚱한 칸에 붙는 사고를 막기 위한 장치다.

확인한 것: 재현성, 다른 이름이면 다른 배치, 공짜 칸 위치 고정, 빙고 판정과 강조,
손상된 링크 안내, 4×4 공짜 칸 잠김, 크기별 필요 문항 수.

## 2026-09-21 — 방식 두 가지와 승리 조건 (`5eb2b35`)

사용자 요청: **초대만 받아 각자 자기 판을 만드는 방식**과 **N줄을 먼저 만든 사람이 승리**.

- `GameMode` 추가. `shared`(지금까지)와 `own`(각자 판).
  `own`은 링크에 설정만 담아서 **약 80자**로 짧다. 문항은 참가자 브라우저에만 남는다.
- `targetLines` 추가. 만들 때 1~5줄에서 고른다.
- 링크 형식을 2판으로 올리되 **1판 링크도 계속 열린다** (`shared`, 1줄로 읽는다).

### 여기서 실제 버그를 하나 잡았다

링크를 바꿔 다른 판으로 이동하면 **앞 판의 참가자 이름과 문항이 그대로 남았다.**
공유판에서 각자 판으로 넘어갈 때 남의 문항이 보일 수 있는 상태였다.
해시만 바뀌면 React가 같은 화면을 재사용하는 것이 원인이라 `<PlayBoard key={payload}>`로 고쳤다.

## 2026-09-21 — 판 위에서 칸을 눌러 채우기 (`911836f`)

사용자 지적: **한 줄에 하나씩 타이핑하는 방식은 폰에서 너무 불편하다.**
빈 판을 먼저 보여주고 칸을 눌러 그 자리에 들어갈 문항을 적는 방식을 원했다.

- `BoardEditor` 신설. 아무 칸이나 골라도 되고, 확인을 누르면 **다음 빈 칸으로 자동 이동**한다.
  칸을 고르면 입력칸에 초점이 가서 폰에서 키보드가 바로 올라온다.
- 만들기를 **설정 → 판 채우기** 두 단계로 나눴다.
- 목록을 이미 가진 사람을 위해 **여러 줄 붙여넣기**를 보조 수단으로 남겼다.
  칸 수를 넘긴 몫은 여분으로 모아 두고, 참가자마다 뽑히는 문항이 달라진다고 알린다.
- 줄 단위 입력만 하던 `CellsField`는 제거했다.

### 섞기와 배치의 충돌

칸을 직접 배치하게 되면서 섞기와 부딪힌다. 자리를 정해도 섞기가 켜져 있으면 참가자는
다른 자리로 받는다. 기능을 없애는 대신 **채우기 화면 맨 위에서 상태를 알려주는 쪽**을 택했다.
섞기를 끄고 배치한 판이 참가자에게 칸 하나까지 똑같이 전달되는 것을 확인했다.

### 아직 없는 것 — 현황판 (M2)

앱은 **"내가" 승리 조건을 채웠다는 것까지만 안다.** 서버가 없어 누가 먼저였는지 비교하지 못한다.
같은 자리에서 하면 말로 확인하면 되지만, 자동 판정은 M2의 몫이다.

### M2 전에 정해야 할 것

**현황판에 어느 칸을 찍었는지까지 보여줄지, 몇 줄 만들었는지만 보여줄지.**
전자가 재미있는 대신 눈치싸움이 사라진다. 아직 미정이다.

### 검증 방식에 대한 솔직한 기록

여기까지의 화면 검증은 **브라우저를 스크립트로 조작한 것**이다. 실제 폰에서 손가락으로
눌러본 것은 아니다. 칸 크기나 입력창 위치 같은 손맛은 실제 기기에서 확인이 필요하다.
