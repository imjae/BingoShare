# BingoShare 기획서

빙고판 설정을 **링크 하나로 보내면**, 받은 사람이 각자 자기 판을 채워서 노는 웹앱.
판은 각자의 기기에 저장되고, **한 번 열어 둔 뒤에는 인터넷 없이도** 고치고 체크한다.

- 최초 작성: 2026-09-21
- 크게 고침: 2026-09-30 — 간소화와 오프라인
- 상태: 배포 중 → https://imjae.github.io/BingoShare/

무엇을 왜 그렇게 했는지의 시간 순 기록은 [WORKLOG.md](WORKLOG.md)에 있다.

---

## 1. 결정된 것

| 항목 | 결정 |
|---|---|
| 흐름 | 보내는 사람은 **설정만** 정하고, 받은 사람이 **자기 문항을 채워** 진행한다 |
| 링크에 담는 것 | 제목 · 판 크기 · 승리 줄 수 (문항 없음) |
| 내 판 저장 | 각자 기기의 브라우저 저장소. 바뀔 때마다 바로 저장 |
| 오프라인 | 한 번 연 뒤에는 인터넷 없이 **열고 · 고치고 · 체크** 한다 (2026-09-30) |
| 문항 수정 | 진행 중에도 언제든 고친다. 체크는 칸 자리에 남는다 (2026-09-30) |
| 승리 조건 | **N줄을 먼저 만든 사람이 승리.** N은 링크를 만들 때 정한다 |
| 호스팅 | 무료 정적 호스팅 (GitHub Pages) |

### 2026-09-30 간소화 — 걷어낸 것

사용자 요청: *"링크를 받은 사람이 빙고판을 작성하고, 저장해서, 인터넷이 안 되는 상황에서도
빙고판을 수정하고 체크할 수 있으면 좋겠다."* 무엇을 남길지는 사용자가 직접 골랐다.

| 걷어낸 것 | 이유 |
|---|---|
| 하나의 판 공유 모드 (만든 사람이 문항을 정함) | 받은 사람이 각자 채우는 흐름 하나로 줄였다 |
| 참가자별 칸 섞기 · 여분 문항 · 이름 시드 배치 | 공유 모드에만 있던 것 |
| 가운데 공짜 칸 | 사용자가 남기지 않았다 |
| "한 번 정하면 못 고침" 잠금 | 요청의 핵심이 "고칠 수 있어야 한다"였다 |
| 링크 길이 경고 (2000자) | 링크에 문항이 없어 넘칠 수 없다 |
| 이름마다 따로 두던 판 | 이제 링크 하나에 판 하나. 이름은 표시용이다 |

**남긴 것:** 승리 조건 N줄, 3×3 · 4×4 · 5×5, 이름 입력.

### 가정 (명시)

- **모바일 우선.** 빙고는 모여서 폰으로 하는 물건이고, 링크도 대부분 폰에서 열린다.
- **로그인 없음.** 이름만 적고 들어간다.

## 2. 서버 없이 가는 방법

- **설정은 링크 안에.** 압축해서 주소의 `#` 뒤에 담는다.
- **내 판은 기기 안에.** 브라우저 저장소(localStorage).
- **앱은 기기 안에.** 서비스 워커가 첫 방문 때 앱 파일을 통째로 받아 둔다.

셋 다 서버가 필요 없어서, 인터넷이 끊겨도 전부 동작한다.
대가는 **남의 판을 볼 수 없다는 것** — 누가 먼저 이겼는지는 같이 하는 사람끼리 확인한다.

> **설계 원칙:** 내 판을 읽고 쓰는 통로를 **`storage.ts` 하나로** 좁혀 둔다.
> 저장 방식을 바꿀 일이 생기면 그 파일만 갈아끼운다.

## 3. 핵심 흐름

```
[만들기]   제목 · 크기 · 승리 줄 수
    ↓
[공유]     초대 링크 복사
    ↓
[참가]     링크 열기 → 이름
    ↓
[채우기]   빈 판에서 칸을 눌러 내 문항 적기
    ↓
[진행]     칸을 눌러 체크  ⇄  문항 고치기        ← 오프라인에서도
```

처음 화면에는 **이 기기에 저장된 판 목록**이 있다. 링크를 잃어버렸거나 주소만 쳐서 들어와도
내 판으로 돌아갈 수 있다.

---

## 4. 규칙

- **크기**: 3×3 / 4×4 / 5×5
- **빙고 판정**: 가로 · 세로 · 대각선
- **승리**: 완성한 줄이 `targetLines` 이상
- **문항을 고쳐도 체크는 자리에 남는다.** "잘못 적은 걸 고쳤다"가 가장 흔한 경우다
- 모든 칸을 채워야 진행을 시작할 수 있다. 고치다가 칸을 비우면 다시 채워야 돌아간다

---

## 5. 데이터 모델

```
Board                        # 링크에 담긴 설정 — 만든 뒤 바뀌지 않는다
  title        제목
  size         3 | 4 | 5
  targetLines  이만큼 줄을 먼저 만들면 승리
  nonce        같은 설정의 링크끼리 구분하는 임의 값

MyBoard                      # 이 기기에 저장된 내 판 — 링크 하나에 하나
  name         표시용 이름
  cells        size×size 개의 문항
  checked      체크한 칸 번호
  (저장할 때 payload · updatedAt을 함께 둔다 — 목록에서 다시 열고 정렬하려고)
```

판 id는 `Board`의 내용에서 끌어낸다(FNV-1a). 같은 링크는 언제나 같은 id라서, 서버 없이도
링크별로 내 판을 찾아낸다.

**왜 `nonce`가 있나.** 링크에 문항이 없으니 제목·크기·줄 수가 같으면 링크가 똑같아진다.
"빙고 · 5×5 · 1줄" 초대 두 개가 한 기기에서 하나의 판으로 합쳐지는 것을 막는다.

## 6. 링크 설계

```
https://<도메인>/#b=<압축한 Board를 주소용 문자로 인코딩>
```

`#` 뒤에 두는 이유:

- 해시는 **서버로 전송되지 않아** 접속 기록에 판 내용이 남지 않는다
- 정적 호스팅에서 서버 설정 없이 동작한다
- 어떤 링크든 **같은 `index.html` 하나로** 열리므로 오프라인 캐시가 단순해진다

### 형식 (3판)

```
[3, 제목, 크기, 0, 0, [], 1, 승리 줄 수, nonce]
```

3~6번 자리는 간소화 전의 섞기 · 공짜 칸 · 문항 · 방식 자리다. 쓰지 않지만 **지우지 않고 고정값을 둔다**
— 자리를 당기면 이미 보낸 링크의 뜻이 바뀐다. 1판 · 2판 링크도 계속 열리고, 문항 · 섞기 · 공짜 칸은
무시한 채 설정만 읽는다. 링크 길이는 제목을 40자 꽉 채워도 200자를 넘지 않는다.

## 7. 오프라인

- **서비스 워커**가 첫 방문 때 `dist`의 파일 전부를 받아 둔다. 목록은 빌드가 자동으로 만든다
- 페이지 요청은 언제나 받아 둔 `index.html`로 답한다
- 새 버전을 배포하면 **한 번 연 뒤, 다음에 열 때** 새 버전이 뜬다
- workbox(`vite-plugin-pwa`)는 쓰지 않았다. 앱 파일이 4개뿐이라 수십 줄로 충분하고,
  의존성 수백 개를 들이는 것보다 무엇을 하는지 한눈에 보이는 편이 낫다

### 한계

- **첫 방문은 인터넷이 있어야 한다.** 그때 앱을 받아 둔다
- 판은 **그 브라우저에만** 있다. 카카오톡 안에서 연 판은 크롬 · 사파리에서 보이지 않는다
- **실제 폰에서 확인하지 않았다.** 특히 아이폰의 카카오톡 인앱 브라우저는 서비스 워커를
  지원하지 않을 가능성이 있다 — 그러면 저장은 되지만 오프라인에서 페이지가 열리지 않는다.
  사파리나 크롬에서 열면 된다
- "홈 화면에 추가"로 앱처럼 설치하는 기능(웹 앱 매니페스트)은 넣지 않았다. 아이폰에서 설치한 앱은
  사파리와 저장소가 분리되어, 사파리에서 채운 판이 보이지 않는 문제가 생긴다

## 9. 기술 스택

- **Vite + React + TypeScript** — 정적 빌드가 나오고, 배포가 파일 업로드로 끝난다
- **Tailwind CSS** — 모바일 우선 레이아웃
- **fflate** — 링크에 담을 설정 압축
- **서비스 워커** — 직접 작성 (`sw/service-worker.js`), 빌드 플러그인이 파일 목록을 붙인다
- **vitest** — 단위 테스트
- **배포**: GitHub Pages (Actions)

## 11. 아직 안 정한 것

- **M2 현황판을 여전히 할지.** 서버가 생기면 오프라인 · 무설치의 단순함이 줄어든다
- **간소화 전에 채워 둔 판을 옮겨 올지.** 지금은 옮기지 않는다 (저장 형식이 바뀌었다).
  옛 링크 자체는 열리지만, 새 판으로 다시 채워야 한다
- 같은 기기를 여러 사람이 돌려 쓰는 경우 — 지금은 링크 하나에 판 하나
- 도메인을 살지, 무료 하위 도메인을 쓸지
